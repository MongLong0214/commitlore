## 11. Token ledger: what a record costs to write, what it saves to read

This section is arithmetic on two measured token counts. The write side is a floor — the session transcript and the model's drafting output are both omitted and both non-negative — so every break-even below is a lower bound on the true one, never an estimate of it. The method is registered in `bench/TOKEN-LEDGER.md`.

Unit: tokens under the product's own `CHARS_PER_TOKEN` constant (`ceil(characters / 4)`), the same unit `delivered_tokens` uses, so the two sides of every ratio share a unit. It is a byte-derived proxy, not a provider tokenizer and not a bill.

### 11.1 Write side — the two terms measurable with no model call

Method: render `buildHarvestPrompt` on the built product with an empty transcript and an empty diff to get the scaffold, then once per record-bearing single-parent commit in `git log b3f569210554aab815a48c21ddef90dce029ba98` with that commit's diff reconstructed as `git diff <sha>^ <sha>`. No model is called.

The history is `b3f569210554aab815a48c21ddef90dce029ba98` and not `HEAD`: it is the commit the delivery run in 11.2 recorded, so both halves of every ratio below describe one repository state rather than two.

| quantity | value |
|---|---:|
| prompt scaffold | 4,788 chars / 4,802 bytes / **1,197 tokens** |
| commits examined | 549 (192 merges) |
| captures priced | 343, carrying 343 record block(s) |
| records excluded | 3 on merge commits, 0 on a root commit |
| staged-diff tokens | mean 8,869, p50 2,342, p95 28,391, max 260,276 |
| prompt tokens per capture | mean 10,064, p50 3,537, p95 29,586, max 261,471 |
| **write floor, with the diff term** | **3,451,848 tokens** over 343 captures |
| **write floor, scaffold only** | **410,571 tokens** over the same captures |
| verification | 0 model tokens in 0 model call(s) |

The staged-diff distribution is reported in full because its mean (8,869) is 3.8x its median (2,342): a few very large commits carry the total, and a reader who takes the mean for a typical capture will be wrong about most of them.

Verification's zero is measured, not assumed: 14 built module(s) reachable from `dist/core/capture-verify.js` and `dist/core/harvest-verify.js` were scanned for a network client and 0 were found. The shipped verifier is local code, so it spends no model tokens by construction.

Three write terms are not here, and none of them can be negative:

- session-transcript: buildHarvestPrompt numbers the transcript into the prompt; the sessions that produced this corpus were never retained, so the term is unrecoverable for these records rather than merely unmeasured
- drafting-output: the tokens a model emits answering the harvest prompt. Needs a model call, and the driver reads one session-total usage object rather than a per-turn ledger, so it could not attribute an answer to that turn even if a call were made
- billing-rate: whether the prompt is charged as fresh input or as a cache read is a provider property this harness never observes

### 11.3 Delivered-token reduction, each with its denominator

Every pair below was fixed before the run. A percentage whose denominator is somewhere else is the figure this market publishes, so the denominator route, its token count and its recall are on the same line as the number.

| subject | denominator | subject / denominator tokens per read | reduction | ratio | subject / denominator recall | recovered pairs |
|---|---|---:|---:|---:|---:|---:|
| `commitlore` | `git-log-path-budgeted` | 488.9 / 643.5 | 24.0% | 1.3x | 81.7% / 42.0% | 1,811 / 931 |
| `commitlore` | `git-log-path` | 488.9 / 1292.0 | 62.2% | 2.6x | 81.7% / 94.4% | 1,811 / 2,093 |
| `commitlore` | `every-record-unbudgeted` | 488.9 / 88122.0 | 99.4% | 180.2x | 81.7% / 92.3% | 1,811 / 2,047 |
| `commitlore-unbudgeted` | `every-record-unbudgeted` | 708.8 / 88122.0 | 99.2% | 124.3x | 92.3% / 92.3% | 2,047 / 2,047 (equal) |
| `commitlore` | `code-only` | 488.9 / 0.0 | — | — | 81.7% / 0.0% | 1,811 / 0 |

- `commitlore` vs `git-log-path-budgeted` — Equal budget. The comparison an agent actually faces, and the only one where the shipped route is both cheaper and higher-recall.
- `commitlore` vs `git-log-path` — Against an unbounded `git log`, which recovers more. Cheaper at lower recall is a trade, not a win, and the recall columns say so.
- `commitlore` vs `every-record-unbudgeted` — Against the whole-repository dump. The largest reduction in the table and the least useful, because nobody has that context.
- `commitlore-unbudgeted` vs `every-record-unbudgeted` — The iso-recovery pair: both are the same projection at a budget that cuts nothing, and both recover the same count. This is the reduction attributable to path scoping alone.
- `commitlore` vs `code-only` — Against reading no history at all. The denominator is zero, so no percentage reduction exists — the shipped route is a token cost here, and a market-shaped percentage cannot express that. What it offers against this route is recall.

An "(equal)" recovered column means the two routes recovered the same **count** of gold pairs. The delivery row records counts and not sets, so it is not evidence that the two recovered the same records, and it is not written as if it were.

A dash in the reduction column is a division by zero, not a missing measurement: a route that delivers nothing has no denominator, and the shipped route costs more than it rather than less. That row is in the table because a token-reduction figure that quietly omits the case where the product is the expensive option is the figure this market publishes.

### 11.4 Break-even, and where none exists

Break-even is the write floor divided by the per-read saving against a named comparator: how many path-scoped reads this repository must serve before the read-side difference covers what its record set cost to write. The comparator's own recall is in the last column, because a token column read alone is the thing this market does.

| comparator | its tokens/read | saving/read | reduction | break-even reads (with diff / scaffold only) | full passes | its recall |
|---|---:|---:|---:|---:|---:|---:|
| `code-only` | 0.0 | -488.9 | — | **none** | — | 0.0% |
| `git-log-path-budgeted` | 643.5 | 154.6 | 24.0% | 22,326 / 2,656 | 21.3 / 2.5 | 42.0% |
| `git-log-path` | 1292.0 | 803.0 | 62.2% | 4,299 / 511 | 4.1 / 0.5 | 94.4% |
| `every-record-budgeted` | 749.0 | 260.1 | 34.7% | 13,272 / 1,579 | 12.7 / 1.5 | 2.2% |
| `every-record-unbudgeted` | 88122.0 | 87633.1 | 99.4% | 39 / 5 | 0.0 / 0.0 | 92.3% |
| `commitlore-unbudgeted` | 708.8 | 219.9 | 31.0% | 15,697 / 1,867 | 15.0 / 1.8 | 92.3% |

The shipped route costs 488.9 tokens per read at 81.7% path recall. A row reading **none** is a comparator that delivers no more tokens than that, so there is no saving for a write cost to amortize against and no read count produces one; the reason is on the JSONL row in `undefined_because`. Against a route that reads no history at all, CommitLore is a net token cost forever, and what it offers there is recall, not tokens.

Both break-even columns are floors. `with diff` charges the staged diff as fresh prompt input; `scaffold only` charges it at nothing, on the assumption it is already in the session's cached prefix. Neither is privileged and the truth is between them — issue #138's lesson was that a break-even which does not say what it counted is underspecified, and that publishing both readings is the fix rather than choosing the flattering one.
